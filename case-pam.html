01 / 07

The problem

On paper it matched CyberArk and Delinea. In a prospect’s hands, it lost the deal in the first hour.

Privileged access management decides who can touch a company’s most sensitive systems: production databases, servers, admin accounts. When it fails, the cost is not a bad experience. It is a breach. So buyers judge a PAM product on one question above all others: can my team run this safely from day one?

Our product had every capability that mattered: vaulting, session recording, access policies, discovery and MFA. Then a prospect’s admin logged in for a proof of concept and found 14 ungrouped navigation items, workflows split across sections, and failures that happened without a word. Within the first hour, they were calling support. Even our own sales engineers sometimes asked me where a feature lived.

02 / 07

The diagnosis

Before touching a screen, I rebuilt 10 real admin scenarios. 140 issues traced back to 4 root causes, and 2 scenarios decided every deal.

The instinct was to redesign the worst screens first. I pushed back for two weeks. Instead, I rebuilt real admin scenarios from customer success call recordings and support tickets: day one onboarding, break glass during a Sev 1, rotating 200+ credentials, and the audit review before a compliance call.

04 / 07

The design

I redesigned in the order my audit set: fix the structure first, then rebuild the two journeys every admin depends on, getting set up and granting access.

FOUNDATION

Navigation by intent

FIXES RC1

The old navigation was organised by database object: System Users, Groups, Certificates, Policies. The new one is organised by what the admin is trying to do. Break glass now lives under Security Ops, and an admin can find it on day one without the docs.

14→5 FLAT ITEMS →
INTENT GROUPS

How I got to five groups: I followed the audit’s own recommendation and grouped all 14 items by workflow phase, meaning the stage of the admin’s job each one serves: setting up, controlling access, running security operations and configuring identity, with an overview on top. Then I walked each audit scenario through the new structure to check that the admin stayed inside one group instead of jumping across the nav.

before, by object → after, by intent
FLOW A

Day one onboarding

FIXES RC3 + RC4
THE OLD PATH
Setting up identity alone meant 14 tasks spread across 4 sections: Authentication, Users, Settings and Two Factor. Role mapping was buried in the second scroll of the SSO config. A failed directory bind gave no reason, whether a wrong URL, wrong credentials or a network issue. The only way to test a synced login was hidden inside “Show Machine Scan Results.” A first-time admin needed a support call every time.
4 sections→1 guided flow
WHAT I EXPLORED
REJECTEDPatch each screen where it lives · The audit showed these gaps were structural. One logical setup sat across four sections, and no screen-level fix could connect them.
REJECTEDOne long setup wizard · The audit had already shown what happens when every field arrives at once. The LDAP form overwhelmed first-time admins.
CHOSENSeven-stage onboarding · It breaks setup into stages an admin can finish and verify one at a time, and it turns setup into the proof of concept itself.
THE DECISION
Seven stages in the order a real deployment happens: connect the directory → discover resources → vault credentials → configure a policy → allocate access → confirm recording → test the first connection. Each stage ends in something the admin can confirm worked before moving on, so a proof of concept moves forward instead of stalling on a silent failure.
FLOW B

Access, from the resource

FIXES RC3
THE OLD PATH
Granting access to one resource meant creating it, attaching a credential, mapping a policy and assigning users, each in a different section, for 4 or more nav visits per resource. Once granted, current access couldn’t be viewed anywhere in the product. Requests arrived only as notification bell items, approval rules lived under Settings, and an approved ticket couldn’t be revoked. Every grant was standing access. JIT, multi-level approval and break glass didn’t exist.
4+ nav visits→1 resource record
WHAT I EXPLORED
REJECTEDUpgrade the notification-bell approvals · The audit found that access governance was a notification, not a workflow. A better bell is still a bell.
REJECTEDA standalone access-request module · Requests in one place, resource config in another and audit history in a third would rebuild the same scatter the audit diagnosed.
CHOSENThe resource as the anchor, with JIT inside it · Credentials, policies, access and audit history all attach to the resource, so one logical task happens in one place.
THE DECISION
Every resource now has its own workspace with tabs for credentials, policy, access, sessions and audit trail. Access is requested and approved from inside the resource and expires when its window closes, so nothing stays standing by default. Requests get a real queue under Tickets & Approvals. Recording and MFA, previously buried three levels deep in Settings, now show on the resource’s security posture. Break glass sits under Security Ops as its own governed path. One resource, one place, one trail.

05 / 07

Making it hold

Navigation fixed where things live. These two fixes made sure admins understood what they saw and knew the moment something broke.

RC2

Language admins already speak

FIXES RC2

New admins spent their first week translating the interface. I rewrote the labels around the words admins use in their own runbooks and audit reports, not the words in our database schema. 

BEFORE · OUR SCHEMAAFTER · THEIR JOBWHY IT MATTERED

RC4

Failures you can see

FIXES RC4

Errors used to fail silently, so admins couldn’t tell what broke. Now errors and reconciliation issues surface inline, on the resource where they happened, along with what to do next. Name one concrete example, such as a failed credential rotation: what the admin saw before and what they see now.

07 / 07

Lessons

In security products, usability is a security control.

The audit was the whole projectEvery decision after it was implementing conclusions the team had already reached together. Two weeks of pushing back on screen redesigns saved months of redesigning the wrong screens.
Frameworks are conversationsRICE and Kano failed because the team used them to avoid talking about what mattered. One honest question did more than two scoring models.
WHAT I GOT WRONGCustomers migrating from another tool skipped onboarding stages, because they already knew what they wanted to set up. A persona is incomplete without knowing what the person is migrating away from.
