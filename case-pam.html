01 / 06

The problem

On paper it matched CyberArk and Delinea. In a prospect’s hands, it lost the deal in the first hour.

Buyers judge a PAM product on one question: can my team run this safely from day one? Ours had every capability that mattered: vaulting, session recording, access policies, discovery, MFA. Then a prospect’s admin logged in for a proof of concept and found 14 ungrouped navigation items, workflows split across sections, and failures that happened without a word. Within the hour, they were calling support. Even our own sales engineers asked me where features lived.

Before the redesign, $742K of PAM pipeline had stalled, and lost deals outweighed won ones $164K to $60K.

This was not a feature gap. It was a comprehension gap, and it was costing us deals.

02 / 06

The diagnosis

Before touching a screen, I audited eight real admin workflows. 136 issues traced back to four root causes, and two workflows decided every deal.

I rebuilt each workflow from customer success calls and support tickets, from day-one onboarding to break glass during a Sev 1, and ran every task the way a first-time admin would.

03 / 06

The decision

136 issues, and a team that wanted to fix features first. I argued for one question instead.

The product and engineering leads wanted to close feature gaps first; the deal-breaker list read like a roadmap. I pushed back for two weeks. The product wasn’t losing on features, it was losing in the first hour. I brought the pipeline data: ten deals had gone cold right after a demo or a quote, and our own audit showed an admin couldn’t connect AD without calling us. We agreed to redesign around experiences first, starting with Credentials, while feature work continued in parallel.

That still left the question of where to start. The PM wanted Kano, the eng lead wanted RICE, and two frameworks the quarter before had given us two different answers. I proposed one blunt filter.

04 / 06

The design

Three moves: navigation organised by intent, setup as seven checked stages, and every access task anchored to the resource.

FOUNDATION

Navigation by intent

FIXES RC1

The old navigation was organised by database object: System Users, Groups, Certificates, Policies. The new one follows the admin’s job: setting up, controlling access, running security operations and configuring identity, with an overview on top. I walked every audit workflow through it to check the admin stayed inside one group. Break glass now sits under Security Ops, findable on day one without the docs.

FLOW A

Day-one onboarding

FIXES RC3 + RC4
THE OLD PATH
Identity setup alone meant 14 tasks across four sections. Role mapping was buried in the second scroll of the SSO config, and a failed directory bind gave no reason. A first-time admin needed a support call every time.
4 sections→1 guided flow
WHAT I EXPLORED
REJECTEDPatch each screen where it lives · One logical setup sat across four sections; no screen-level fix could connect them.
REJECTEDOne long setup wizard · The audit had already shown first-time admins overwhelmed when every field arrived at once.
CHOSENSeven-stage onboarding · Each stage can be finished and verified on its own, which turns setup into the proof of concept itself.
THE DECISION
Seven stages, in the order a real deployment happens: directory → resources → credentials → policy → access → recording → first connection. Each stage ends in something the admin can confirm worked, so a proof of concept moves forward instead of stalling on a silent failure. Skipping is allowed, with the cost named first, and the dashboard resumes from the exact step.

Every stage ends in proof

FLOW B

Access, from the resource

FIXES RC3
THE OLD PATH
Granting access to one resource took four or more nav visits: create it, attach a credential, map a policy, assign users. Once granted, access couldn’t be viewed anywhere, requests arrived as notification-bell items, and an approved ticket couldn’t be revoked. Every grant was standing access.
4+ nav visits→1 resource record
WHAT I EXPLORED
REJECTEDUpgrade the notification-bell approvals · A better bell is still a bell.
REJECTEDA standalone access-request module · It would rebuild the same scatter the audit diagnosed.
CHOSENThe resource as the anchor, with JIT inside it · One logical task, one place.
THE DECISION
Every resource now has its own workspace, with tabs for credentials, policy, access, sessions and audit trail. Access is requested and approved inside the resource and expires when its window closes, so nothing stays standing by default. Requests get a real queue under Tickets & Approvals, and break glass has its own governed path under Security Ops.

RC4

Failures you can see

FIXES RC4

When a directory sync failed, nothing said so. The user list looked healthy while four people couldn’t log in. Now errors surface inline, on the resource where they happened, with what broke and what to do next.

Outcome

$800K in new PAM sales the quarter after release. Deals that stalled at proof of concept started closing.

Before it shipped

I re-ran the audit’s tasks on the new design: every setup and access task the redesign covered could be completed without a dead end or a support call. We also tested the new navigation with existing customers.

06 / 06

Lessons

In security products, usability is a security control.

The diagnosis was the designEvery decision after it implemented conclusions the team had already reached together. Two weeks of pushing back on a features-first roadmap saved months of building the wrong things.
WHAT I GOT WRONGCustomers migrating from another tool skipped onboarding stages, because they already knew what they wanted to set up. A persona is incomplete without knowing what the person is migrating away from. Next: an import path for teams moving from another vault, and a skip-ahead for admins who’ve run PAM before.
