01 · THE PROBLEM

On paper it matched CyberArk and Delinea. In a prospect’s hands, it lost the deal in the first hour.

Buyers judge a PAM product on one question: can my team run this safely from day one? Ours had every capability that mattered: vaulting, session recording, access policies, discovery, MFA. Then a prospect’s admin logged in for a proof of concept and found 14 ungrouped navigation items, workflows split across sections, and failures that happened without a word. Within the hour, they were calling support. Even our own sales engineers asked me where features lived.

Before the redesign, $742K of PAM pipeline had stalled, and lost deals outweighed won ones $164K to $60K.

03 · THE DECISION

136 issues, and a team that wanted to fix features first. I argued for one question instead.

The product and engineering leads wanted to close feature gaps first; the deal-breaker list read like a roadmap. I pushed back for two weeks. The product wasn’t losing on features, it was losing in the first hour. I brought the pipeline data: ten deals had gone cold right after a demo or a quote, and our own audit showed an admin couldn’t connect AD without calling us. We agreed to redesign around experiences first, starting with Credentials, while feature work continued in parallel.

That still left the question of where to start. The PM wanted Kano, the eng lead wanted RICE, and two frameworks the quarter before had given us two different answers. I proposed one blunt filter.

04 · THE DESIGN · NAVIGATION BY INTENT

Organised by what the admin is doing, not by database object.

Three moves: navigation organised by intent, setup as seven checked stages, and every access task anchored to the resource.

FOUNDATION · FIXES RC1
14→5flat items → intent groups
The old navigation was organised by database object: System Users, Groups, Certificates, Policies. The new one follows the admin’s job: setting up, controlling access, running security operations and configuring identity, with an overview on top. I walked every audit workflow through it to check the admin stayed inside one group. Break glass now sits under Security Ops, findable on day one without the docs.

04 · THE DESIGN · FLOW A

Seven stages, each one verified.

Day-one onboarding. Fixes RC3 and RC4.

THE OLD PATHIdentity setup alone meant 14 tasks across four sections. Role mapping was buried in the second scroll of the SSO config, and a failed directory bind gave no reason. A first-time admin needed a support call every time.
4 sections→1 guided flow
WHAT I EXPLORED
Patch each screen where it livesREJECTEDOne logical setup sat across four sections; no screen-level fix could connect them.
One long setup wizardREJECTEDThe audit had already shown first-time admins overwhelmed when every field arrived at once.
Seven-stage onboardingCHOSENEach stage can be finished and verified on its own, which turns setup into the proof of concept itself.
THE DECISIONSeven stages, in the order a real deployment happens: directory → resources → credentials → policy → access → recording → first connection. Each stage ends in something the admin can confirm worked, so a proof of concept moves forward instead of stalling on a silent failure. Skipping is allowed, with the cost named first, and the dashboard resumes from the exact step.

Every stage ends in proof.

01 · DIRECTORY142 users and 18 groups synced, with a preview of one real user’s role.
02 · RESOURCESA scan finds 12 hosts; the admin adds only what PAM should protect.
03 · CREDENTIALSEach one is tested the moment it’s entered.
04 · POLICYOne safe default: recording on, MFA required, 30-minute idle timeout.
05 · ACCESSLifelong access is allowed but flagged, with working hours one click away.
06 · RECORDINGCoverage shown as a share of resources, the number an auditor asks for.
07 · TESTA simulated first connection: reachable, authenticated, policy applied, recording ready.

04 · THE DESIGN · FLOW B

One resource, one place, one trail.

Access, from the resource. Fixes RC3.

THE OLD PATHGranting access to one resource took four or more nav visits: create it, attach a credential, map a policy, assign users. Once granted, access couldn’t be viewed anywhere, requests arrived as notification-bell items, and an approved ticket couldn’t be revoked. Every grant was standing access.
4+ nav visits→1 resource record
WHAT I EXPLORED
Upgrade the notification-bell approvalsREJECTEDA better bell is still a bell.
A standalone access-request moduleREJECTEDIt would rebuild the same scatter the audit diagnosed.
The resource as the anchor, with JIT inside itCHOSENOne logical task, one place.
THE DECISIONEvery resource now has its own workspace, with tabs for credentials, policy, access, sessions and audit trail. Access is requested and approved inside the resource and expires when its window closes, so nothing stays standing by default. Requests get a real queue under Tickets & Approvals, and break glass has its own governed path under Security Ops.

04 · THE DESIGN · LANGUAGE + ERRORS

Language admins already speak, failures they can see.

RC2

Language admins already speak

I rewrote the labels around the words admins use in their own runbooks and audit reports.

System Users→Credentials
Admins looked for server passwords under a label that sounded like people
Users→People
Clashed with System Users, the most common first-day mix-up
All Tickets→Tickets & Approvals
Access requests read as a support inbox, not a governance step
Rotator Instance→Admin Account
A developer label on every rotation setup
RC4

Failures you can see

When a directory sync failed, nothing said so. The user list looked healthy while four people couldn’t log in. Now errors surface inline, on the resource where they happened, with what broke and what to do next.

BEFOREA plain user list, nothing wrong on screen.
AFTER4 users didn’t sync from Active Directory. Their accounts are missing an email attribute. Map the attribute in Identity Config, then re-run sync.

06 · LESSONS

In security products, usability is a security control.

01The diagnosis was the design.Every decision after it implemented conclusions the team had already reached together. Two weeks of pushing back on a features-first roadmap saved months of building the wrong things.
WHAT I GOT WRONGCustomers migrating from another tool skipped onboarding stages, because they already knew what they wanted to set up.A persona is incomplete without knowing what the person is migrating away from. Next: an import path for teams moving from another vault, and a skip-ahead for admins who’ve run PAM before.
